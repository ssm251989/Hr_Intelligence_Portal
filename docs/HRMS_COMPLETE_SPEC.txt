B. DEPLOYMENT & TENANCY MODEL (one codebase, two deployment shapes)
---------------------------------------------------------------------
DECISION: every client gets MODE 1 (its own installation). MODE 2 is
kept in the code (TENANCY_MODE=multi) but is NOT deployed at launch.
Same Docker image supports:

  MODE 1 - DEDICATED ("client's own environment")
    TENANCY_MODE=single
    One stack per client on AWS (India region), own Postgres (RDS),
    own Redis, own S3 bucket, own subdomain and/or own custom domain.
    Control plane still exists but holds exactly one tenant row.

  MODE 2 - SHARED SaaS (many clients, one stack)
    TENANCY_MODE=multi
    Control-plane DB + one Postgres DATABASE PER TENANT (default
    isolation) or shared DB with tenant_id + Row-Level Security
    (for small/trial tenants). Isolation chosen per tenant.

  A tenant can be MOVED from shared -> dedicated with the
  `hrctl tenant export/import` tooling (Part 13).

Every tenant-owned table carries `tenant_id UUID NOT NULL` even in
DB-per-tenant mode (enables RLS mode, safe export/import, and
defence-in-depth). Postgres RLS policies are created on every tenant
table: `USING (tenant_id = current_setting('app.tenant_id')::uuid)`.

Tenant resolution order (middleware `TenantResolverMiddleware`):
  1. Custom domain / subdomain (Host header) -> control_plane.tenant_domains
  2. `X-Tenant-Slug` header (for API/mobile clients, only if enabled)
  3. In single mode: the only tenant.
  JWT carries `tid`; request is rejected (403) if JWT tid != resolved tenant.

Tenant context propagates to: DB session (per-tenant engine cache +
`SET app.tenant_id`), Redis key prefix `t:{tenant_id}:`, object storage
prefix `tenants/{tenant_id}/`, Celery task headers, logs (structlog
field), metrics labels, outbound webhooks.

H. CROSS-CUTTING STANDARDS (apply in every part)
---------------------------------------------------------------------
- IDs: UUIDv7. Timestamps: timestamptz UTC; display in resolved tz.
- Effective dating for HR facts: effective_from / effective_to.
- Soft delete (deleted_at) for business records; hard delete only via
  privacy erasure workflow (dry-run report first - existing discipline).
- Every mutation writes audit_log (who, tenant, entity, before/after
  diff, request_id, ip). Audit is append-only (no UPDATE/DELETE grants).
- Idempotency-Key header supported on all POSTs that create records.
- Transactional outbox for every domain event (no lost emails:
  the orphaned-token class of bug is prevented structurally).
- All external calls go through connectors with timeout, retry with
  backoff, circuit breaker, and a delivery/attempt log row.
- PII fields (PAN, Aadhaar, bank a/c, passport, salary, health) are
  encrypted at column level and masked in API unless permission
  `<module>.<entity>.view_sensitive` is held.
- Pagination, filtering, sorting: one shared query-spec contract.
- Every list page keeps the existing RefreshButton behaviour.
- Human-in-the-loop at every real hiring/people decision (unchanged).
- API versioned under /api/v1. OpenAPI published per tenant with only
  enabled modules.

5B - WORKFLOW & APPROVAL ENGINE
-----------------------------------
1. Definitions (versioned, per tenant)
   workflow_definitions(id, tenant_id, key, name, module, version,
     status[draft|published|retired], trigger_json, graph_json,
     created_by, published_at)
   trigger types: event (any domain event), field_change(entity, field,
     from/to), schedule(cron, tenant tz), date_relative(entity.date
     +/- N days e.g. probation_end - 15d), manual(button on entity),
     api/webhook, form_submit.
   node types:
     condition (JSONLogic), switch (multi-branch),
     approval {approvers: resolver list, mode sequential|parallel|any|
       quorum N, sla, reminders, escalation to resolver, allow
       delegate, allow send-back, comments required on reject},
     task {assignee resolver, form_id, due},
     action {set_field, create_record, send_notification(template),
       call_connector(purpose, op), webhook, generate_document,
       run_ai(prompt_key) -> REQUIRES human review node after it},
     wait {duration | until date | until event}, parallel/join,
     sub_workflow, end.
   approver resolvers: user, role-in-scope, manager(level n),
     department_head, hrbp_of(employee), position_holder, expression,
     skip-if-same-as-requester, auto-approve rule.
2. Runtime
   workflow_instances(id, tenant_id, definition_id+version, entity_type,
     entity_id, status, context_json, started_by, started_at, ended_at)
   workflow_steps(id, instance_id, node_id, status, assignee, due_at,
     acted_by, action, comment, payload, started_at, ended_at)
   - Engine runs on Celery; each node transition is one DB transaction
     + outbox events (no half-done state).
   - Timers via `workflow_timers` table polled by beat (idempotent).
   - Running instances keep their version; new ones use latest.
   - Admin can reassign, skip (audited), retry failed action nodes.
3. Unified Inbox: GET /api/v1/inbox - all pending approvals/tasks
   across modules; approve/reject from email via signed
   one-time action links (reuse NegotiationToken pattern generically as
   `action_tokens`).
4. Visual builder (React Flow): drag nodes, property panels with
   rjsf forms, validation (unreachable nodes, missing approvers),
   simulate with a sample record (dry-run shows path + who approves).
5. Seed default workflows (generic, editable): job requisition
   approval, offer approval, BGV decision, asset request,
   onboarding checklist, probation confirmation, transfer/promotion,
   resignation & clearance, profile change approval.

   export, RefreshButton (existing behaviour), empty states that
   explain the next step.

   drafts for long forms, clear required markers, mobile-friendly.

   draft -> preview/simulate -> publish -> version history -> revert.

   settings page - never a raw 500.
